## 1. 文件目的

本文件描述 TradeGuard 現有的使用者角色、功能需求、主要業務規則、系統介面、安全與資料完整性要求，以及已知限制，作為測試、維護和後續需求討論的共同依據。

本規格以目前 `backend-java/`、`frontend-next/`、`README.md`、CI 設定及測試為準。未實作或僅列於舊版構想文件的功能，均不視為本系統現有能力。

## 2. 系統概述

TradeGuard 是教學與作品集用途的虛構證券交易模擬系統，提供商品主檔管理、限價委託、價格／時間優先撮合、規則式市場監視、案件雙人覆核、稽核鏈驗證、帳本對帳及日終 XML 報表。

系統主要流程如下：

```text
帳號註冊／登入
    → 商品與行情查詢
    → 建立或取消限價委託
    → 撮合及成交
    → 規則式監視與警示
    → 人工提報案件及獨立覆核
    → 稽核鏈驗證與帳本對帳
    → 日終作業與 XML 報表
```

本系統不連接真實交易所、不處理真實資金，也不構成投資建議或違規判定工具。

## 3. 目標與範圍

### 3.1 系統目標

- 提供可操作的模擬證券交易端到端流程。
- 以明確驗證規則和確定性撮合順序展示交易系統核心概念。
- 記錄委託及重要操作，並在啟動時重播事件、驗證持久化狀態一致性。
- 以規則式警示輔助人工調查，透過提報者與覆核者分離維持四眼原則。
- 提供稽核完整性檢查、交易帳本對帳及日終報表。

### 3.2 本版本範圍

**包含：**公開市場讀取、使用者登入／登出與交易員公開註冊、管理員帳號及商品管理、限價委託與取消、基本撮合、兩類監視警示、案件覆核、稽核與對帳、日終作業及 XML 報表、CI 自動檢查。

**不包含：**真實交易或券商連線、資金／持倉／交割管理、市價單及其他進階委託、電子郵件驗證、忘記密碼／密碼重設、公開建立管理員或監控／稽核帳號、人工案件調查工作流以外的執法判定、完整交易所規則、規章 RAG、價量異常日線資料來源、SSE／WebSocket 即時推播及多實例分散式撮合。

## 4. 使用者角色與權限

| 角色 | 建立方式 | 可用功能 |
|---|---|---|
| 未登入訪客 | 不適用 | 瀏覽公開行情、商品資訊、委託簿、近期成交與撮合規則；註冊交易員帳號；登入。 |
| `TRADER` 交易員 | 公開註冊或管理員建立 | 建立限價買／賣委託；查詢自己的委託；取消自己的未完成委託。 |
| `SURVEILLANCE` 監控人員 | 管理員建立 | 檢視警示與案件；提報警示為案件；核准或駁回其他監控人員提報的案件。 |
| `AUDITOR` 稽核員 | 管理員建立 | 唯讀檢視警示與案件；驗證稽核鏈；執行帳本對帳；讀取日終 XML 報表。 |
| `ADMIN` 管理員 | 初始 bootstrap 或管理員建立 | 管理商品及角色帳號；唯讀檢視警示與案件；驗證稽核鏈、對帳及讀取日終 XML 報表。 |

角色授權必須由後端執行；前端的導覽顯示和頁面存取限制只改善操作體驗，不構成安全邊界。

## 6. 主要業務規則

1. **交易單位：**預設整股委託量為 1,000 股倍數。
2. **價格限制：**委託限價預設不得超出商品參考價格上下 10%。
3. **升降單位：**

   | 價格範圍 | 最小跳動 |
   |---|---:|
   | \(0 \leq P < 10\) | 0.01 |
   | \(10 \leq P < 50\) | 0.05 |
   | \(50 \leq P < 100\) | 0.1 |
   | \(100 \leq P < 500\) | 0.5 |
   | \(500 \leq P < 1000\) | 1 |
   | \(P \geq 1000\) | 5 |

4. **交易時段：**預設台北時區週一至週五 09:00 至 13:30；開始時間包含、結束時間不包含。
5. **撮合排序：**價格優先，其次依資料庫產生的商品序號排序；成交價為先到委託價格。
6. **委託冪等：**冪等範圍為同一使用者及同一 `client_order_id`；相同請求重送不可重複成交，內容不同時須拒絕。
7. **案件四眼原則：**提報帳號與覆核帳號必須不同；每案件僅能完成一次覆核。
8. **警示意義：**監視警示僅作為人工審查依據，不代表已確認違規或法律判定。
9. **日終成功條件：**委託、成交、事件三方核對及序號檢查無差異時才產生並保存日報。
10. **示意性質：**上述市場參數是教學示例，不保證符合現行交易所規則，亦不得用於真實交易決策。

| `GET` | `/api/market/{symbol}/info` | 查詢商品資訊 | 公開 |
| `GET` | `/api/market/{symbol}/book` | 查詢委託簿 | 公開 |
| `GET` | `/api/market/{symbol}/trades` | 查詢近期成交 | 公開 |
| `POST` | `/api/orders` | 建立限價委託 | `TRADER` |
| `GET` | `/api/orders/mine` | 分頁查詢本人委託 | `TRADER` |
| `DELETE` | `/api/orders/{id}` | 取消本人委託 | `TRADER` |
| `GET` | `/api/alerts` | 分頁查詢警示 | `SURVEILLANCE`、`AUDITOR`、`ADMIN` |
| `POST` | `/api/alerts/{id}/case` | 提報案件 | `SURVEILLANCE` |
| `GET` | `/api/cases` | 分頁查詢案件 | `SURVEILLANCE`、`AUDITOR`、`ADMIN` |
| `POST` | `/api/cases/{id}/review` | 覆核案件 | `SURVEILLANCE` |
| `GET` | `/api/audit/verify` | 驗證稽核鏈 | `AUDITOR`、`ADMIN` |
| `GET` | `/api/audit/reconcile` | 帳本核對 | `AUDITOR`、`ADMIN` |
| `GET` | `/api/reports/daily.xml?date=YYYY-MM-DD` | 讀取日終 XML | `AUDITOR`、`ADMIN` |
| `POST` | `/internal/eod?date=YYYY-MM-DD` | 執行日終核對／報表 | 有效 `X-EOD-Token` |

### 7.2 通用 API 行為

- 請求與回應採 JSON；日終報表為 XML。
- 新增資源使用 `201 Created`；參數驗證或 JSON 格式錯誤使用 `400`；未登入使用 `401`；權限不足或來源不允許使用 `403`；資源不存在使用 `404`；重複／資料衝突使用 `409`；登入失敗鎖定可回 `429`；登入狀態服務不可用可回 `503`。
- API 錯誤使用共用 JSON 欄位 `timestamp`、`status`、`error`、`message`、`path` 及可選 `details`。
- 分頁 API 預設採分頁結構；後端最大 page size 為 100。
- 帶有 `Origin` 的非安全 API 方法只接受設定允許的來源。

## 8. 資料需求與完整性

### 8.1 核心資料

- 使用者：帳號、密碼雜湊、角色、啟用狀態與建立時間。
- 商品：商品代碼、名稱、啟用狀態、參考價格及每商品序號計數。
- 委託：使用者、商品、方向、限價、委託量、已成交量、狀態、序號及用戶端冪等 ID。
- 成交：商品、買賣雙方委託、成交價格、數量及成交時間。
- 委託事件：委託接受、成交及取消的事件紀錄。
- 警示與案件：規則、成交關聯、嚴重度、提報者、覆核者、決定、備註及時間。
- 稽核紀錄：操作者、操作、細節、UTC 時間、前一筆雜湊與本筆雜湊。
- 日終資料：業務日期、對帳結果、差異、報表內容及 SHA-256。

### 8.2 儲存責任

- PostgreSQL 是使用者、商品、委託、成交、警示、案件、事件、稽核與日終資料的持久事實來源。
- Redis 用於登入失敗鎖定、JWT 撤銷、行情／委託簿快取及監視短期視窗資料；Redis 快取丟失不得被當作交易事實。
- 公開行情快取在 Redis 不可用時可回源 PostgreSQL；登入狀態相關操作在 Redis 不可用時採 fail-closed。

## 9. 非功能需求

| 類別 | 需求 |
|---|---|
| 安全 | 密碼以 BCrypt 雜湊；JWT 僅存 HttpOnly Cookie；敏感秘密只由環境變數注入，不提交至版控。 |
| 授權 | 後端逐路由驗證角色；使用者只可存取本人委託；公開註冊不可取得高權限角色。 |
| 跨站請求 | 設定精確 CORS allowlist、允許 credentials；非安全 API 方法驗證來源。 |
| 隱私 | 角色受限的日報不使用跨使用者共用快取；錯誤回應不得洩漏密碼或 token。 |
| 一致性 | 委託、成交及事件以資料庫交易維持一致；資料列鎖／唯一約束處理併發及重複請求。 |
| 可恢復性 | 透過持久委託事件重播恢復未結委託；重播／序號檢查失敗時服務不應正常啟動。 |
| 可稽核性 | 重要操作記錄至鏈式稽核紀錄；提供驗證與獨立帳本對帳 API。 |
| 可用性 | 健康檢查提供 `/api/health`；錯誤需明確回傳，不得以成功狀態掩蓋下游失效。 |
| 可維護性 | 後端使用 Java 21、Spring Boot；前端使用 Next.js App Router、React、TypeScript；資料庫結構以 Flyway migration 管理。 |
| 可測試性 | GitHub Actions 對 PR 和 `main` push 執行後端驗證、前端 lint/build 及相依套件稽核；PR 另執行 Dependency Review。 |
| 效能／即時性 | 前端以輪詢更新市場資料；目前沒有低延遲 SLA，亦不承諾 WebSocket 等即時推播。 |
| 可擴展性限制 | 撮合狀態與序號依賴單一後端的持久化及記憶體恢復模型；本版本不宣稱支援多實例平行撮合。 |

## 10. 驗收條件

下列條件用於驗收主要功能；正式環境驗收須另以實際部署環境及其設定執行。

1. 訪客可讀取公開商品／行情，但不能呼叫受保護寫入操作。
2. 註冊後建立的帳號角色必為 `TRADER`；即使請求附帶 `ADMIN` 角色也不能提升權限。
3. 正確帳密登入後可由 `/api/auth/me` 取得使用者角色；登出後同一 Cookie 不再通過認證。
4. `ADMIN` 能新增、編輯、啟用／停用和刪除商品，非管理員寫入操作遭拒。
5. `TRADER` 可建立合法委託；交易時段、商品狀態、數量倍數、價格限制或升降單位不合法時，後端拒絕委託。
6. 可成交委託依價格及系統序號撮合；支援部分成交；相同 idempotency key 重送不建立額外成交。
7. 交易員只能查詢及取消自己的委託；已完成／無未成交量委託不可再取消。
8. 符合已實作監視規則的成交可產生警示；警示可提報為案件，但提報者不能覆核自己的案件。
9. 稽核鏈未損壞時驗證成功；資料不平衡時對帳回報差異且日終不產生成功報表。
10. 日終成功後，具 `AUDITOR` 或 `ADMIN` 權限者可依日期讀取並下載 XML；其他角色遭拒。
11. 前端頁面呈現載入、空資料、成功及錯誤狀態；瀏覽器不接觸 JWT 原文。
12. PR／`main` CI 執行後端測試、前端 lint/build 及依賴檢查；部署健康檢查端點回應成功。

## 11. 已知限制與未完成事項

- 公開註冊只提供 `TRADER`；目前沒有信箱驗證、忘記密碼、密碼重設、帳號停用／鎖定管理頁。
- 目前只實作 `WASH_TRADE` 和 `CLOSING_MARKUP` 監視規則；20 日量價異常與 spoofing 未實作。
- 市場監視規則為簡化門檻式示意，會有誤報及漏報，不可用於判定違規。
- 價格升降單位、漲跌幅、交易單位及交易時間不是完整官方規則。
- 前端管理清單主要讀取有限筆數（最多 100 筆），完整跨頁管理仍可擴充。
- 事件與稽核紀錄目前以應用層 insert-only 存取模式保護；尚未加入資料庫權限或 trigger 層級的不可變防護。
- Redis 不承載最終交易事實；登入鎖定和 JWT 撤銷依賴 Redis 可用性。免費 Redis 重啟可能清空暫態資料。
- GitHub Actions CI 執行測試與安全檢查；Render／Vercel 的部署由平台連結 GitHub 後各自觸發，不代表 CI 通過才部署。
- 正式部署設定、正式環境登入及完整雲端端到端流程，須以當前 Render、Vercel、Neon 和 GitHub 設定及執行結果另行確認。
- RAG 規章問答、AI 助理、市價單、WebSocket／SSE、真實交易所資料及 C# 對帳工具均不屬於目前已交付功能。
