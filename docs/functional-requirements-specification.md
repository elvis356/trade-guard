## 1. 文件目的

本文件定義 TradeGuard 的目標、範圍、使用者角色、功能需求、主要業務規則、外部介面、安全與資料完整性要求及驗收條件，作為設計、開發、測試與驗收的需求基準。

本文件描述系統「應提供」的行為，不代表相關功能已完成或已通過驗收。實作方式、實際完成狀態與部署結果應由設計文件、測試結果及版本紀錄另行追蹤，不應反向取代需求基準。

## 2. 系統概述

TradeGuard 是教學與作品集用途的虛構證券交易模擬系統，提供商品主檔管理、限價委託、價格／時間優先撮合、規則式市場監視、案件雙人覆核、稽核鏈驗證、帳本對帳及日終 XML 報表。

系統主要流程如下：

```text
帳號註冊／登入
    → 商品與行情查詢
    → 建立或取消限價委託
    → 撮合及成交
    → 規則式監視與警示
    → 人工提報案件及獨立覆核
    → 稽核鏈驗證與帳本對帳
    → 日終作業與 XML 報表
```

本系統不連接真實交易所、不處理真實資金，也不構成投資建議或違規判定工具。

## 3. 目標與範圍

### 3.1 系統目標

- 提供可操作的模擬證券交易端到端流程。
- 以明確驗證規則和確定性撮合順序展示交易系統核心概念。
- 記錄委託及重要操作，並在啟動時重播事件、驗證持久化狀態一致性。
- 以規則式警示輔助人工調查，透過提報者與覆核者分離維持四眼原則。
- 提供稽核完整性檢查、交易帳本對帳及日終報表。

### 3.2 本版本範圍

**包含：**公開市場讀取、使用者登入／登出與交易員公開註冊、管理員帳號及商品管理、限價委託與取消、基本撮合、規則式監視警示、案件覆核、稽核與對帳、日終作業及 XML 報表。

**不包含：**真實交易或券商連線、資金／持倉／交割管理、市價單及其他進階委託、電子郵件驗證、忘記密碼／密碼重設、公開建立管理員或監控／稽核帳號、人工案件調查工作流以外的執法判定、完整交易所規則、規章 RAG、延伸量價異常及 spoofing 監視規則、SSE／WebSocket 即時推播及多實例分散式撮合。

## 4. 使用者角色與權限

| 角色 | 建立方式 | 可用功能 |
|---|---|---|
| 未登入訪客 | 不適用 | 瀏覽公開行情、商品資訊、委託簿、近期成交與撮合規則；註冊交易員帳號；登入。 |
| `TRADER` 交易員 | 公開註冊或管理員建立 | 建立限價買／賣委託；查詢自己的委託；取消自己的未完成委託。 |
| `SURVEILLANCE` 監控人員 | 管理員建立 | 檢視警示與案件；提報警示為案件；核准或駁回其他監控人員提報的案件。 |
| `AUDITOR` 稽核員 | 管理員建立 | 唯讀檢視警示與案件；驗證稽核鏈；執行帳本對帳；讀取日終 XML 報表。 |
| `ADMIN` 管理員 | 初始 bootstrap 或管理員建立 | 管理商品及角色帳號；唯讀檢視警示與案件；驗證稽核鏈、對帳及讀取日終 XML 報表。 |

角色授權必須由後端執行；前端的導覽顯示和頁面存取限制只改善操作體驗，不構成安全邊界。

## 5. 功能需求

### 5.1 身分驗證與帳號管理

| ID | 需求 | 權限／規則 |
|---|---|---|
| FR-AUTH-01 | 系統應提供帳號與密碼登入，成功後回傳使用者角色及到期時間。 | 公開端點；帳號以不區分大小寫方式正規化。 |
| FR-AUTH-02 | 登入成功後，系統應以 HttpOnly、SameSite=Lax Cookie 保存短效登入憑證，不得將憑證放入前端可讀取的頁面資料。 | Cookie 應限定必要 API 路徑；正式環境應啟用 Secure。 |
| FR-AUTH-03 | 系統應提供登出，撤銷目前登入憑證並使瀏覽器 Cookie 過期。 | 撤銷狀態應保留至憑證到期；狀態服務不可用時不得略過撤銷檢查。 |
| FR-AUTH-04 | 系統應提供目前登入者查詢，供前端初始化登入狀態與角色導覽。 | 需有效登入憑證。 |
| FR-AUTH-05 | 系統應允許公開建立交易員帳號。 | 註冊固定建立 `TRADER`，不得接受或套用用戶端提交的角色；帳號 3–50 字元，只允許英數字、點、底線、連字號；密碼至少 12 字元。 |
| FR-AUTH-06 | 管理員應能建立 `TRADER`、`SURVEILLANCE`、`AUDITOR` 或 `ADMIN` 帳號。 | 僅 `ADMIN`；密碼不得以明文保存或在 API 回應中輸出。 |
| FR-AUTH-07 | 系統應限制登入失敗次數並在達門檻時暫時鎖定登入。 | 依帳號計算失敗次數；登入狀態服務不可用時應拒絕處理，不得視為驗證成功。 |
| FR-AUTH-08 | 系統應使用統一錯誤格式回報無效帳密、驗證錯誤、重複帳號及登入鎖定。 | 不得藉錯誤訊息區分帳號不存在與密碼錯誤。 |
| FR-AUTH-09 | 系統應支援管理員查詢帳號清單及單一帳號。 | 僅 `ADMIN`；清單支援分頁。 |

### 5.2 商品主檔與公開市場資料

| ID | 需求 | 權限／規則 |
|---|---|---|
| FR-MKT-01 | 訪客及登入者應能瀏覽商品清單、單一商品資訊及參考價格。 | 公開讀取；清單支援分頁。 |
| FR-MKT-02 | 訪客及登入者應能查詢市場報價、指定商品委託簿快照及近期成交。 | 公開讀取；資料應標示其更新時間或非即時性。 |
| FR-MKT-03 | 管理員應能建立、查詢、整筆修改、部分修改及刪除商品。 | 僅 `ADMIN` 可寫入；商品代碼不得重複。 |
| FR-MKT-04 | 管理員應能啟用或停用商品；交易員只能對有效且啟用的商品下單。 | 後端需再次驗證，不能只依賴前端商品清單。 |
| FR-MKT-05 | 訪客及登入者應能在公開首頁 `/` 瀏覽市場總覽，並由報價卡前往 `/market/[symbol]`。 | 報價應定期更新；需呈現空資料／載入／錯誤狀態，無報價時提示管理員建立並啟用商品。交易表單僅在受 `TRADER` 角色限制的 `/trade`。 |
| FR-MKT-06 | 前端商品頁應顯示商品資訊、委託簿及近期成交。 | 資料應定期更新，並明確呈現其非即時保證。 |

### 5.3 限價委託與撮合

| ID | 需求 | 權限／規則 |
|---|---|---|
| FR-ORD-01 | 交易員應能建立限價買進或賣出委託。 | 僅 `TRADER`；請求包含商品代碼、方向、限價、數量和 UUID 格式 `client_order_id`。 |
| FR-ORD-02 | 後端應驗證商品狀態、數量單位、價格升降單位、參考價格漲跌幅及交易時段。 | 數量必須為 1,000 股的倍數；漲跌幅預設 ±10%；升降單位採本規格所列級距；台北時區週一至週五 09:00（含）至 13:30（不含）。規則屬教學示意，不宣稱完整符合交易所規章。 |
| FR-ORD-03 | 撮合應先依價格優先，再依商品內遞增系統序號決定時間優先。 | 不得以用戶端時間排序；買盤價格較高者、賣盤價格較低者優先。 |
| FR-ORD-04 | 可成交委託應支援一次撮合多筆對手委託及部分成交。 | 成交價採先到委託價格；未成交數量保留於委託簿。 |
| FR-ORD-05 | 重送同一交易員、同一 `client_order_id` 且請求內容相同的請求時，系統應回傳既有結果，不得重複委託或成交。 | 同一 key 的請求內容不同時須拒絕並回報衝突。 |
| FR-ORD-06 | 交易員應能分頁查看自己的委託及其狀態、價格、數量和成交量。 | 僅回傳目前登入者自己的委託。 |
| FR-ORD-07 | 交易員應能取消自己仍有未成交量的委託。 | 不得取消他人委託；已成交／已取消且無剩餘量者拒絕取消；已成交部分不回滾。 |
| FR-ORD-08 | 系統應記錄委託接受、成交及取消事件，並在啟動時重播事件、驗證持久化狀態一致性。 | 事件與對應交易資料需具原子一致性；重播或序號核對不一致時不得正常啟動。 |
| FR-ORD-09 | 前端應提供限價下單表單、本人委託清單及可用時的取消操作。 | 前端需呈現拒絕原因及載入／空資料狀態；後端為最終驗證者。 |

### 5.4 市場監視與案件處理

| ID | 需求 | 權限／規則 |
|---|---|---|
| FR-SURV-01 | 系統應在成交後套用規則式監視條件並保存警示。 | 警示須可追溯至成交、商品、規則及發生時間；重複處理不得重複建立同一警示。 |
| FR-SURV-02 | 系統應產生同一帳戶同時出現在成交買賣方的 `WASH_TRADE` 警示。 | 警示是人工調查線索，不等於違規認定。 |
| FR-SURV-03 | 系統應依可設定的尾盤時間窗、參考價偏離比例與買方成交量門檻產生 `CLOSING_MARKUP` 警示。 | 初始參數為尾盤 5 分鐘、偏離 5%、視窗成交量 5,000 股；參數應可設定。僅供示意及人工判讀。 |
| FR-SURV-04 | 監控人員應能分頁查看警示及案件。 | `SURVEILLANCE`、`AUDITOR`、`ADMIN` 可讀；稽核員及管理員唯讀。 |
| FR-SURV-05 | 監控人員應能將警示提報為案件。 | 僅 `SURVEILLANCE`；同一警示不得重複建立案件。 |
| FR-SURV-06 | 監控人員應能核准或駁回案件，並提供必填審核備註。 | 僅 `SURVEILLANCE`；案件提報者不得覆核自己的案件；已完成案件不可再次覆核。 |
| FR-SURV-07 | 案件提報及覆核結果應寫入稽核紀錄。 | 需保留執行者、操作種類、關聯案件及時間等稽核資訊。 |

### 5.5 稽核、對帳與日終報表

| ID | 需求 | 權限／規則 |
|---|---|---|
| FR-AUD-01 | 系統應將重要委託、成交、案件提報與覆核操作寫入可驗證的鏈式稽核紀錄。 | 稽核內容應包含操作者、操作、關聯資料、時間及完整性驗證所需資訊；併發寫入不得破壞鏈結。 |
| FR-AUD-02 | 稽核員及管理員應能驗證稽核紀錄的內容雜湊、前後連結及目前鏈頭。 | `GET /api/audit/verify`；發現完整性錯誤時回報失敗，而非回報成功。 |
| FR-AUD-03 | 稽核員及管理員應能核對委託、成交與委託事件帳本。 | `GET /api/audit/reconcile`；至少檢查委託接受／取消事件、成交量、對手關係、事件成交量及商品序號連續性。 |
| FR-AUD-04 | 系統應提供受秘密憑證保護的日終作業入口。 | `POST /internal/eod`；以 `X-EOD-Token` 驗證，支援可選業務日期；未設定／不符 token 回 401。 |
| FR-AUD-05 | 日終作業應保存每次對帳結果；僅在對帳平衡時產生並保存該日 XML 報表。 | 不平衡時記錄失敗結果並回傳衝突，不得發布成功報表；成功報表應附完整性校驗資訊。 |
| FR-AUD-06 | 稽核員及管理員應能依台北業務日期讀取日終 XML 報表並在前端檢視／下載。 | `GET /api/reports/daily.xml?date=YYYY-MM-DD`；受角色授權；須避免跨使用者共用快取。 |
| FR-AUD-07 | 系統應支援依排程或人工觸發日終作業。 | 排程時間、行事曆及執行平台由部署設計定義；呼叫須經服務端秘密憑證驗證。 |

## 6. 主要業務規則

1. **交易單位：**預設整股委託量為 1,000 股倍數。
2. **價格限制：**委託限價預設不得超出商品參考價格上下 10%。
3. **升降單位：**

   | 價格範圍 | 最小跳動 |
   |---|---:|
   | \(0 \leq P < 10\) | 0.01 |
   | \(10 \leq P < 50\) | 0.05 |
   | \(50 \leq P < 100\) | 0.1 |
   | \(100 \leq P < 500\) | 0.5 |
   | \(500 \leq P < 1000\) | 1 |
   | \(P \geq 1000\) | 5 |

4. **交易時段：**預設台北時區週一至週五 09:00 至 13:30；開始時間包含、結束時間不包含。
5. **撮合排序：**價格優先，其次依系統產生的商品序號排序；成交價為先到委託價格。
6. **委託冪等：**冪等範圍為同一使用者及同一 `client_order_id`；相同請求重送不可重複成交，內容不同時須拒絕。
7. **案件四眼原則：**提報帳號與覆核帳號必須不同；每案件僅能完成一次覆核。
8. **警示意義：**監視警示僅作為人工審查依據，不代表已確認違規或法律判定。
9. **日終成功條件：**委託、成交、事件三方核對及序號檢查無差異時才產生並保存日報。
10. **示意性質：**上述市場參數是教學示例，不保證符合現行交易所規則，亦不得用於真實交易決策。

| `POST` | `/api/cases/{id}/review` | 覆核案件 | `SURVEILLANCE` |
| `GET` | `/api/audit/verify` | 驗證稽核鏈 | `AUDITOR`、`ADMIN` |
| `GET` | `/api/audit/reconcile` | 帳本核對 | `AUDITOR`、`ADMIN` |
| `GET` | `/api/reports/daily.xml?date=YYYY-MM-DD` | 讀取日終 XML | `AUDITOR`、`ADMIN` |
| `POST` | `/internal/eod?date=YYYY-MM-DD` | 執行日終核對／報表 | 有效 `X-EOD-Token` |

### 7.2 通用 API 行為

- 請求與回應採 JSON；日終報表為 XML。
- 新增資源使用 `201 Created`；參數驗證或 JSON 格式錯誤使用 `400`；未登入使用 `401`；權限不足或來源不允許使用 `403`；資源不存在使用 `404`；重複／資料衝突使用 `409`；登入失敗鎖定可回 `429`；登入狀態服務不可用可回 `503`。
- API 錯誤使用共用 JSON 欄位 `timestamp`、`status`、`error`、`message`、`path` 及可選 `details`。
- 分頁 API 預設採分頁結構；後端最大 page size 為 100。
- 帶有 `Origin` 的非安全 API 方法只接受設定允許的來源。

## 8. 資料需求與完整性

### 8.1 核心資料

- 使用者：帳號、密碼雜湊、角色、啟用狀態與建立時間。
- 商品：商品代碼、名稱、啟用狀態、參考價格及每商品序號計數。
- 委託：使用者、商品、方向、限價、委託量、已成交量、狀態、序號及用戶端冪等 ID。
- 成交：商品、買賣雙方委託、成交價格、數量及成交時間。
- 委託事件：委託接受、成交及取消的事件紀錄。
- 警示與案件：規則、成交關聯、嚴重度、提報者、覆核者、決定、備註及時間。
- 稽核紀錄：操作者、操作、細節、UTC 時間、前一筆雜湊與本筆雜湊。
- 日終資料：業務日期、對帳結果、差異、報表內容及 SHA-256。

### 8.2 儲存責任

- 使用者、商品、委託、成交、警示、案件、事件、稽核與日終資料須有持久儲存；快取或暫態儲存不得成為交易事實的唯一來源。
- 系統應區分持久業務資料與可重建或暫態資料；快取遺失不得造成交易資料遺失或不一致。
- 身分驗證所需狀態無法確認時，系統不得略過驗證或撤銷檢查而放行受保護操作。

| 效能／即時性 | 市場資料須定期更新並呈現資料時間；本版本不要求低延遲 SLA 或即時推播。 |

## 10. 驗收條件

下列條件用於驗收主要功能；正式環境驗收須另以實際部署環境及其設定執行。

1. 訪客可讀取公開商品／行情，但不能呼叫受保護寫入操作。
2. 註冊後建立的帳號角色必為 `TRADER`；即使請求附帶 `ADMIN` 角色也不能提升權限。
3. 正確帳密登入後可由 `/api/auth/me` 取得使用者角色；登出後同一 Cookie 不再通過認證。
4. `ADMIN` 能新增、編輯、啟用／停用和刪除商品，非管理員寫入操作遭拒。
5. `TRADER` 可建立合法委託；交易時段、商品狀態、數量倍數、價格限制或升降單位不合法時，後端拒絕委託。
6. 可成交委託依價格及系統序號撮合；支援部分成交；相同 idempotency key 重送不建立額外成交。
7. 交易員只能查詢及取消自己的委託；已完成／無未成交量委託不可再取消。
8. 符合第 5.4 節定義條件的成交可產生警示；警示可提報為案件，但提報者不能覆核自己的案件。
9. 稽核鏈未損壞時驗證成功；資料不平衡時對帳回報差異且日終不產生成功報表。
10. 日終成功後，具 `AUDITOR` 或 `ADMIN` 權限者可依日期讀取並下載 XML；其他角色遭拒。
11. 前端頁面呈現載入、空資料、成功及錯誤狀態；瀏覽器不接觸 JWT 原文。
12. 交付建置須通過自動化測試與靜態檢查；服務存活與就緒狀態端點須依第 7.1 節定義回應。
